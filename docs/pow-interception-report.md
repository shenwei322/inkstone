# POW 人机验证拦截率测试报告

测试对象：`backend/internal/service/pow_service.go`（自研 PoW v2）
测试日期：随仓库本次交付一起固化，`cd backend && go test ./...` 可随时复现。

> **本报告记录的是加固前的实测结果**，作为问题依据保留。
> 针对其中发现的问题所做的优化及其效果，见
> [pow-optimization-report.md](./pow-optimization-report.md)。
> 一句话概括：XFF 限流绕过与跨场景挪用已修复（拦截率 0% → 100%），
> 服务端单次校验从 3.77ms 降到 0.07ms（约 50 倍），
> signal 的定位已在代码与文档中改为诚实的"UX 门槛"。

---

## 一、结论摘要

**PoW 只能挡住"没实现协议的机器人"，挡不住"实现了协议的机器人"。**

拦截率不是一个数，而是取决于攻击者复刻协议的程度：

| 攻击者类型 | 拦截率 |
|---|---|
| 不知道有这个字段的裸脚本 | **100%** |
| 知道字段名、没实现求解器的脚本 | 97.7% – 100% |
| 实现了协议但没有真实浏览器交互的脚本 | **0%** |
| 真人浏览器 | 0%（误杀率 0） |

代码注释里承诺的"本地交互信号让纯 HTTP 脚本无法伪造"**不成立**——signal 是完全可合成的（见发现 1）。
注释里承诺的"内存带宽削弱 GPU/ASIC 集群优势"**基本不成立**（见发现 4）。

真正提供防护的只有两件事：一次性挑战（防重放）和 SHA-256 工作量成本。而工作量成本又被限流架空了一半（见发现 3）。

## 二、测试方法

环境限制导致测试分两层，均未依赖数据库：

- **服务层白盒测试**（`internal/service/pow_intercept_test.go` 等）
  走 `CaptchaService.Verify`，即 handler 层真实调用的那道门。
  利用 `SettingsService` 的 nil-db 分支返回 `settingDefaults` 快照，在包内改写快照即可模拟后台配置（与既有 `lap_service_test.go` 的 `NewLapService(nil)` 惯例一致）。
- **HTTP 层测试**（`internal/handler/pow_challenge_test.go`）
  按 `main.go` 相同方式装配 `POST /api/v1/pow/challenge` 与 `middleware.IPRateLimit`。

无法完成的部分（如实说明）：
- 本机无 PostgreSQL、无 Docker 守护进程，**没能跑起真实 server 做端到端 HTTP 全链路测试**；handler 层是用自建 gin 路由镜像 `main.go` 装配完成的。
- 无 gcc/cgo，`-race` 不可用，**数据竞争未能验证**。
- `pwsh` 在受限沙箱下无法启动（0xC0000144），仅在 full-access 下可用。

## 四、拦截率 vs 攻击者算力投入

难度 3（期望 4096 次尝试/次验证），判定是否拦截完全由"算力预算/期望尝试数"决定：

| 算力投入 | 预算 | 样本 | 实测拦截 | 理论拦截 |
|---|---|---|---|---|
| 1/4096 | 1 | 300 | 100.0% | 100.0% |
| 1/1024 | 4 | 400 | 100.0% | 99.9% |
| 1/256 | 16 | 400 | 100.0% | 99.6% |
| 1/64 | 64 | 400 | 99.2% | 98.4% |
| 1/8 | 512 | 400 | 86.5% | 88.2% |
| 1倍（期望） | 4096 | 500 | 34.6% | 36.8% |
| 2倍 | 8192 | 400 | 10.2% | 13.5% |
| 3倍 | 12288 | 400 | 7.8% | 5.0% |

实测贴合 `(1-1/16^d)^budget` 模型。

**关键认知**：投入正好等于"期望尝试次数"时，成功率只有 `1-e^-1 ≈ 63%`，要 3 倍工作量才到 95%。
PoW 的门槛是**软的、按算力比例衰减的曲线**，不是"做不出来就过不去"的硬门槛。
底层哈希均匀性已用 400 万次尝试独立证实（多次运行偏差分别为 0.47σ / 0.78σ / 2.03σ）。

## 六、前后端算法一致性

用 `frontend/lib/pow.ts` + `frontend/lib/sha256.ts` 的**真实源码**（tsc 原样编译后 require，未做任何手工改写）与 Go 后端对拍：

- 24 组参数组合（memory 1–32MB × rounds 1–16）× 2 条前端实现路径（纯 JS sha256 + WebCrypto.subtle），**摘要 48/48 逐位一致**。
- 前端真实 `solvePow` 解出后端签发的难度 4 挑战（nonce=62203，62204 次尝试，785ms），后端 `powDigest` 重算确认满足难度并接受。

算法层面**没有漂移**，这一项是可靠的。复现方式：`node pow-parity/run.mjs`。

## 七、发现与风险评估

### 发现 1（高）：signal 校验对机器人零识别能力

`verifyPowSignal` 只做三件事：格式 `{m|k|t}:{unix_ms}:{x}:{y}`、事件数 ≥ min_events、时间戳落在 `[issuedAt-2s, now+2s]`。

问题在于时间戳的信息量：**脚本刚刚才请求过 challenge，它本来就大致知道 challenge 是什么时候签发的**，直接填 `time.Now()` 即可通过。坐标值也无任何校验。

实测：
- A10（脚本解题 + 合成 signal，全程无浏览器）：**拦截率 0%**
- 对照实验 `min_events=0`：同样通过，说明 min_events 没有增加攻击者的任何真实成本
- A12（signal 与 challenge 无绑定）：独立生成一份 signal 配任意新挑战，**拦截率 0%**

代码注释 `pow_service.go:29` 声称"纯 HTTP 脚本不带这个信息，必须额外复刻整套构造逻辑才能过服务端格式与时间窗校验"——实际上"复刻整套构造逻辑"就是几行 `fmt.Sprintf`，不构成对抗性成本。`pow-captcha.tsx:34` 的注释同理。

**建议**：要么把 signal 当作纯 UX 门槛（要求用户动一下鼠标）而不要在安全文档里宣称它防机器人；要么改成真正难以伪造的形式——例如要求 signal 与 challenge 绑定（HMAC）、要求事件流覆盖最小时间跨度且严格递增、要求坐标分布具备非统计学特征。当前形态下，它只挡住"漏字段"的脚本。

### 发现 2（中）：挑战未绑定场景与请求

`Issue()` 只记参数快照，`Verify(action, ...)` 只查该场景开关。因此：

- A13 实测：为 login 签发的挑战可直接用于 comment，**拦截率 0%**
- 挑战也未绑定 IP、未绑定待提交的邮箱/用户名/评论内容

后果：(a) 可以预求解一批挑战再分发消费，把 PoW 成本与实际攻击请求解耦；(b) 一个场景的挑战池可被挪用到另一个场景。

**建议**：把 scene（以及可选的 IP、请求指纹摘要）写进挑战记录，Verify 时比对。

### 发现 3（高）：X-Forwarded-For 可伪造，IP 限流被完全作废

`middleware.ClientIP` 无条件优先读取客户端自带的 `X-Forwarded-For`，而 `main.go` 从未调用 `router.SetTrustedProxies(...)`，gin 默认信任全部代理。

实测（`TestPowChallengeRateLimitBypassViaXFF`）：

```
对照组（无 XFF，同源 IP）      ：放行  30 / 100 次，限流生效=true
攻击组（逐请求伪造 XFF）        ：放行 200 / 200 次，限流被绕过=true
```

任何能直连后端的客户端（绕过 Nginx、公网直 IP 部署、容器网络内横向访问）只要每次请求换一个 XFF 值，就能作废**所有** IP 限流：PoW 挑战池 30/分钟、登录 10/15 分钟、注册 5/小时、评论 10/10 分钟、友链申请 5/小时、以及全局 API 600/分钟。

这条同时削弱 PoW 本身的价值：PoW 的成本威慑只有在"每个 IP 的尝试次数受限、且每次尝试都要付成本"时才成立。

**建议**：
1. `main.go` 显式调用 `router.SetTrustedProxies([]string{你的 Nginx 内网网段})`，收紧 gin 的信任范围；
2. `middleware.ClientIP` 改为只在已知代理场景读取 XFF，或者改为读 `gin` 配置好的 `c.ClientIP()`，不要自己再读一遍头；
3. 若部署上必须直连，考虑加一层"同一 IP 任意 XFF 变化模式"的异常检测。

### 发现 4（中）："内存硬化"基本不成立

`powDigest` 每次调用重建整个 memoryMB 表（`pow_service.go:288`），而每个候选只随机读 `rounds` 个字——默认 4 个字，16 字节。

也就是说：攻击者每试一个 nonce，从内存表里读 16 字节；而 8MB 的表在主流服务器 CPU 上能整个装进 L2/L3 缓存。所谓"内存带宽瓶颈削弱 GPU/ASIC 集群优势"并没有真正发生。

实测支持这一点：默认配置下 65536 次期望尝试（难度 4）客户端耗时约 60–85 ms，全部成本几乎就是 `(rounds+1)` 次 SHA-256，GPU 可以近乎完美地并行化。

配套的实测证据（第五节）：服务端校验耗时随 memoryMB 线性放大（1MB 0.68ms → 32MB 14.4ms，21.3×），说明服务端那 4.5ms 里绝大部分是**重建表**，而不是安全相关的哈希判定——1MB 时只花 0.68ms。

**建议**：
- 若目标是内存硬化，需要大幅提高每候选的表访问次数和访问跨度（否则现有参数形同虚设）；
- 至少把服务端的表重建优化掉：表是 challenge 的确定性函数，可以在签发时算一次缓存到挑战记录里；1MB 档实测 0.68ms 说明哈希判定本身很便宜；
- 后台把 memoryMB 调到 32 目前只会线性增加服务端 CPU（14ms/次），不会明显提高攻击者成本，性价比很差。

### 发现 5（低/信息项）：服务端与客户端成本比 0.1，方向正确

服务端 4.5ms、客户端 65ms，约 16 倍差距。这个比例对 PoW 来说是健康的。配合发现 4 的表重建优化后差距还能进一步拉大。

## 八、验证过的正确行为

以下行为经测试确认符合代码注释的承诺，可以放心：

- 场景未开启一律放行，绝不锁死用户（`TestPowSceneDisabledFailsOpen`）
- 挑战一次性消费，重放必被拦（A11，100%）
- 过期挑战失效，nonce 正确也不行（`TestPowTTLExpiry`）
- 挑战池满后 `Issue` 报错、业务侧全部拒绝（`TestPowChallengePoolLimit`）
- 越界参数全部 clamp 回默认值而非 panic 或放飞（`TestPowDifficultyClamp`）
- 前后端算法 48/48 一致，`/pow/challenge` 响应字段与类型正确
- 密码学层面无异常：4M 次尝试命中比例偏离均匀分布 ≤2.1σ
